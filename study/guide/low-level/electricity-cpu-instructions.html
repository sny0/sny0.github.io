第2章 論理回路・CPU・命令 ​

このページで案内すること ​

論理回路からレジスタ、命令の実行へ進むための学習計画・概要です。回路や命令セットの概説を足場に、実際のコードとの対応を観察します。論理回路・CPU設計を順に説明する専用本文は未整備です。

関連する辞典本文・実践 ​

  • 関数呼び出し・レジスタ・呼出規約で、命令を読む際の具体例を確認できます。
  • キャッシュ・分岐予測・SIMDでは、命令実行と性能の関係を扱います。

学ぶ理由 ​

ゲームループの1周は、CPUが命令列を実行することで実現される。 「CPUは命令をメモリから取ってきて解読して実行する機械」という実感がないと、 アセンブリ(第4章)は記号の暗記になり、最適化(第18章)は迷信になる。 また「分岐が重い」「16ms以内に終わらせる」といった現場の会話は、 CPUの動作モデルを持っていて初めて意味が分かる。

到達目標 ​

  • トランジスタ→論理ゲート→加算器→ALU という積み上げを概念的に説明できる
  • CPUの基本サイクル(フェッチ→デコード→実行)を説明できる
  • レジスタ・プログラムカウンタ・命令セット(ISA)とは何かを説明できる
  • クロック周波数・IPCと「処理が16.6msに収まるか」の関係を説明できる
  • 分岐予測・パイプラインの存在を知り、なぜ分岐ミスが高価か説明できる

前提知識 ​

第1章(2進数・ビット)。

学ぶ内容 ​

  1. 電気から論理へ(深入りしない)
    • トランジスタ=電気で制御するスイッチ。これだけでよい(半導体物理は不要)
    • NANDゲートから AND/OR/NOT/XOR が作れる
    • 組み合わせ回路: 半加算器→全加算器→nビット加算器→ALU
    • 順序回路: フリップフロップ=1bit記憶 → レジスタ、クロック=拍
  2. CPUの構造
    • レジスタファイル、ALU、制御ユニット、プログラムカウンタ(PC/RIP)
    • フェッチ→デコード→実行→(メモリアクセス)→書き戻し のサイクル
    • 命令セットアーキテクチャ(ISA)= ハードとソフトの契約書
      • x86-64(PC/Xbox/PS5)と ARM64(Switch/スマホ/Apple)の2大勢力
      • CISCとRISCの思想の違い(現代では内部的に収斂している)
  3. 命令とは何か
    • 機械語命令 = 「操作コード + オペランド」のビット列
    • 転送(mov)、演算(add/mul)、分岐(jmp/je)、コール(call/ret)の4分類で ほぼ全てのプログラムができている
    • 条件分岐 = フラグレジスタ + 条件ジャンプ(if文の正体)
  4. 性能の基礎モデル
    • 1コアのCPU実行時間のモデル: 命令数 × 平均CPI ÷ クロック周波数。 命令の並列実行や待ちの影響は平均CPIに表れる。実際の経過時間にはOSの待機等も関わる
    • 60fps = 約16.67ms/フレーム。1コアが3GHzで動き続けると仮定すると 約5000万クロック/フレーム。ゲームがその全てを使えるという保証ではない
    • 現代CPUの高速化(概要のみ、詳細は発展編): パイプライン、スーパースカラ、アウトオブオーダー実行、分岐予測
    • 分岐予測ミスは命令のやり直しを生む。損失はCPU・コード・周辺の待ちに依存する。 15〜20サイクル等の値は特定条件の目安であり、全CPU共通の定数ではない
  5. (演習)Nand2Tetrisで16bit CPUを自作する
    • NANDゲートだけから始めてCPUとアセンブラを作る。この教本で 唯一の「回路づくり」。1〜6章のハードウェア部だけでOK

重要概念 ​

  • ストアドプログラム方式: 命令はメモリ上のただのデータ。 だからコンパイラ(データとして機械語を出力するプログラム)が成立する
  • ISAは契約: 同じx86-64バイナリがIntelでもAMDでも動く理由
  • 実行時間には予算がある: 目標フレーム時間と動作周波数を仮定して見積もり、実測する。 ゲームプログラミングは常にこの予算内でのやりくり
  • CPUは推測で走る: 分岐予測・投機実行。「素直なコードは速い」の根拠

ゲーム開発との関係 ​

現場の事象この章の知識
「この処理、1フレームに収まる?」サイクル予算の感覚
ホットループでの仮想関数/分岐が重い分岐予測ミスのコスト
PC/PS5とSwitchでビルドを分けるISAの違い(x64 vs ARM64)
「CPUバウンド」という言葉CPUの実行モデル
インライン展開・ループ展開が効く命令数とパイプラインの関係

演習 ​

  1. Nand2Tetris プロジェクト1〜5 を完走せよ(HDLでALUとCPUを作る)。 これがこの章のメイン演習。約20〜40時間。
  2. 3GHzのCPUで60fpsのゲームを動かすとき、1フレームあたりのサイクル数を 計算せよ。1命令1サイクルと仮定したら何命令実行できるか。
  3. C++で「ソート済み配列」と「ランダム配列」それぞれに対し if (a[i] > 128) sum += a[i]; のループを計測し、速度差を確認せよ (有名な分岐予測実験)。差の理由を説明せよ。
  4. 電卓アプリを使わずに、x * 10 をシフトと加算だけで計算する式を書け (コンパイラが実際にやる最適化)。

理解度チェック ​

  1. CPUの基本サイクル(フェッチ→デコード→実行)を、PC(命令ポインタ)の 役割を含めて説明せよ。
  2. 「if文」はCPUレベルでは何になるか? なぜ予測ミスが遅いのか?
  3. ISAとは何か。x86-64とARM64のバイナリに互換性がないのはなぜか?
  4. 3GHz・IPC=4のCPUは、16.6msで理論上何命令実行できるか?
  5. ストアドプログラム方式だからこそ可能になっているツールを2つ挙げよ (例: コンパイラ、JIT、セーブステート付きエミュレータ...)

この章がゲームのどこで使われているか ​

ゲームループの1周(約16.67ms): 3GHzの1コアなら約5000万クロックの時間幅
┌────────────────────────────────────────────┐
│ while (running) {                           │
│   入力処理     ← mov/cmp/jne… 命令数は実装次第 │
│   ゲーム更新   ← 物理・AI・アニメ等の命令列  │
│   描画コマンド ← API呼び出しも結局は命令列    │
│ }                                           │
└────────────────────────────────────────────┘
     ▲ すべての行が「フェッチ→デコード→実行」の積み重ね
     ▲ パッド入力の検知もUSBドライバの命令実行(第8章)
     ▲ GPUもまた別種の命令を実行するプロセッサ(第11章)
