第3部 演習 — GoFデザインパターン ​

パターン名の暗記ではなく「問題→選択肢→判断」の練習です。まず自力で解いてから解答を開いてください。

問1. 概念確認(逆引き) ​

次の要求に対して第一候補となるパターン(または「パターン不要」)を答えてください。

  1. ミドルウェアSDKの型と作法がコード全域に漏れている
  2. バフが複数同時に乗り、時間で切れる
  3. 「敵を倒したら」に反応するシステムが5つある
  4. レベルエディタにUndoが必要
  5. ボタンが2つある設定画面を作る
  6. 起動時に全読みしているアセットで、メモリピークが問題になった
解答
  1. Adapter(境界に変換層)。2. Decoratorのリスト方式(修飾パイプライン)。3. Observer(発生源は5システムを知らない)。4. Command(逆操作)またはMemento(スナップショット)、規模で選ぶ。5. パターン不要(直接書く)。6. Proxy(遅延ロード)+事前ロードAPI。——複数解が成立する問いもある。理由を言えることが重要。

問2. コード読解 ​

cpp
// C++20
class Door {
public:
    void Update(Player& p) { state_ = state_->Update(*this, p); }
    // ...
private:
    IDoorState* state_;   // Open/Closed/Lockedのいずれか
};
  1. これは何パターンですか。StrategyではなくそのパターンだとU判断できる根拠は?
  2. state_ が生ポインタでも安全に設計できる方法を1つ挙げてください。
解答
  1. State。Update の戻り値で自分自身が次の状態を決めて遷移している(Strategyなら外部が装着し、自分では替わらない)。
  2. 状態オブジェクトを状態ごとに1個のstaticインスタンス(状態自身がデータを持たない設計)にして共有する——寿命が問題にならなくなる。あるいはunique_ptr所有に変える。前者はアロケーションも消えるため、頻繁に遷移するゲームでは定石(Stateの変形)。

問3. 問題のあるコードの改善 ​

「武器強化画面を開くたび、強化値計算・素材チェック・UI更新・保存のコードが UpgradeScreen::OnClick に600行」——この画面で使えるパターンを2つ以上組み合わせた改善案の骨格(クラス名と責務のみ)を書いてください。

解答の要点

例: 計算・素材チェックを UpgradeService(ロジック、UIなし)に抽出(SRP)。画面部品間の連動は UpgradeScreen をMediatorに。保存はイベント発行(Observer)か SaveFacade(Facade)へ。強化結果のプレビューは計算を純関数にすれば無料でつく。**「どのパターンか」より「変更理由ごとの分離が先、パターンはその手段」**という順序が正解の骨格。

問4. 設計比較 ​

「敵のドロップ抽選」を (a) Enemy::RollDrop() に直書き、(b) IDropStrategy 注入、(c) ドロップテーブルをデータ化(Type Object方向)で比較し、「運用でドロップ率を毎週調整するタイトル」ならどれを選ぶか判断してください。

解答の要点

(a) 最小コスト。調整=コード修正+ビルド+配信。(b) 抽選アルゴリズムが複数あるなら意味があるが、率の調整だけなら過剰。(c) 率・内容の調整がデータ配信で完結——毎週調整の運用ならこれ一択に近い。パターン(Strategy)は「アルゴリズムの差」に効く道具で、「数値の差」にはデータ化が効く、という区別が本問の核心。

問5. デバッグ問題 ​

Observer実装で「ステージを2周すると、敵死亡時のスコア加算が2倍になる」バグが出ました。最も疑わしい原因と、恒久対策を答えてください。

解答

原因: ステージ開始時に購読(Subscribe)し、終了時に解除していない——2周目で同じリスナーが二重登録され、通知が2回届く。対策: 解除を購読と対で書く(C#: OnDisableで-=、C++: 購読トークンのRAII化)、または二重登録を検出するアサート。Observerの「解除忘れ」はリークだけでなく多重実行としても現れる、が教訓。

問6. 説明問題 ​

「DecoratorとProxyとAdapterは全部『包む』パターンですよね。何が違うんですか?」への回答を3文で書いてください。

解答例

包んだ結果のインターフェースと目的が違う。Adapterは形を変えて合わないものを繋ぎ、Proxyは同じ形のままアクセスを管理し(遅延・保護)、Decoratorは同じ形のまま機能を積み増す(何枚も重ねる前提)。「形が変わるか」「目的が管理か追加か」の2軸で見分けるとよい(Adapter/Proxy/Decorator)。

問7. 小規模実装問題 ​

ミニ実装課題(検証サンプルを土台にしてよい):

  1. Command: 盤上の駒の移動をUndo付きで実装(samples/pattern_command.cppを拡張し「駒の生成」コマンドを追加)
  2. Observer+Stateの連携: 敵の状態遷移(巡回→追跡)をイベントで通知し、BGM切替の購読者を付ける
  3. Flyweight: 弾種データ共有の弾幕(1万発)を実装し、共有なし版とのメモリ差をsizeof計算で示す
取り組みの指針

各サンプル(samples/pattern_*.cpp)がコンパイル可能な出発点。評価基準は「動く」ことより、(a) 所有権が明確か(誰がdeleteするか)、(b) パターンの可変点が要件と一致しているか、(c) 「これはパターンなしでも書けたか?」に答えられるか。3問とも「なしで書いた場合」との差分を一言で書けたら合格。
