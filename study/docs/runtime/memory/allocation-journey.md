# malloc・newから解放まで — アロケータとOSの境界

`new Enemy` や `malloc(64)` を書くと、アプリケーションが使える記憶域を得ます。そのたびに、OSが新しい物理RAMを64バイト渡しているわけではありません。**既に管理している領域を再利用する処理、必要に応じてOSへ追加を求める処理、オブジェクトを初期化する処理**を分けると、内部の流れを追えます。

このページはC++17/20の通常の単一オブジェクトの `new` / `delete` と、正のサイズを指定する `malloc` / `free` を中心に説明します。言語の契約と、典型的な実装の例を区別します。pool・arena・placement new・`std::pmr` の使い分けは[アロケータとプール](/runtime/memory/allocators-and-pools.html)、アドレス変換の詳解は[仮想メモリ](/os/virtual-memory.html)を参照してください。

## 1. 「確保」を3つの層に分ける

| 層 | 決めること | 代表的な名前 |
| --- | --- | --- |
| 言語・ライブラリ | 必要なサイズ、整列条件、初期化、失敗、後片付けの契約 | `malloc`、new式、`operator new`、delete式 |
| アロケータ | 空いている領域の探索・再利用、領域の補充、管理情報、並行アクセスの扱い | サイズクラス、フリーリスト、スレッド用キャッシュ |
| OS・ハードウェア | アドレス空間、ページの状態・保護、物理メモリへの対応 | Windowsの`VirtualAlloc`、ページ表、TLB |

**アロケータ**は、記憶域を要求に応じて配り、返された領域を管理する仕組みです。通常はページより小さい要求も扱います。対してOSの仮想メモリ管理はページや領域を扱います。アロケータは、その大きな単位の中から小さな単位を供給できます。

言語規格は、すべての処理系に同じヒープ構造やOS APIを要求していません。WindowsのCRT、Linuxのglibc、ゲームで採用する別のアロケータでは内部が異なります。Windowsにも、ページを扱うAPIとは別に、小さなブロックを管理する[ヒープAPI](https://learn.microsoft.com/en-us/windows/win32/memory/heap-functions)があります。

## 2. mallocとnew式は何を約束するか

### malloc: バイト数で記憶域を要求する

`malloc(n)` は要求を満たす領域へのポインタを返し、確保できなければnullポインタを返します。返った領域の内容は初期化済みの値として扱えません。要求が64バイトでも、整列条件や管理情報のため、実装が内部で使う量は64バイトより大きいことがあります。Microsoft CRTの[ `malloc` の説明](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/malloc?view=msvc-170)にも、この区別があります。

`malloc` はC++の型を受け取らず、その型のコンストラクタを呼びません。`Enemy` がメモリ以外の資源も初期化するなら、領域を得ただけで、その初期化が済んだことにはできません。なお、C++20には一部の型のオブジェクトを暗黙に生成する規則があります。**オブジェクトの存在に関する規則と、型固有のコンストラクタを実行することは別です。** 詳細はC++作業草案の[ `c.malloc` ](https://eel.is/c++draft/c.malloc)で確認できます。

### new式: 記憶域を得て、オブジェクトを初期化する

次は処理を分けて読むためのコード断片です。

```cpp
// C++17 — 説明用の断片
struct Enemy {
    int hp;
    explicit Enemy(int initialHp) : hp(initialHp) {}
};

Enemy* enemy = new Enemy(100);
// 1. Enemyに必要なサイズと整列条件を満たす記憶域を得る
// 2. その記憶域でEnemyを初期化し、この例ではコンストラクタが動く

delete enemy;
// 通常のdelete: Enemyを破棄してから、対応する解放関数へ記憶域を返す
```

`new Enemy(100)` という**new式**と、記憶域取得を担う関数 **`operator new`** は別です。呼ぶ確保関数は、グローバルの関数、クラス側に定義した関数、整列条件を受け取る形式などから規則に従って選ばれます。`operator new` 自体が `Enemy` のコンストラクタを呼ぶ、という説明にすると役割を取り違えます。

普通のnew式でも、すべての型の全バイトがゼロになるわけではありません。例えば `new int` と `new int{}` は初期化の指定が異なります。クラスでは、選ばれたコンストラクタやメンバーの初期化規則を確認します。[Microsoftのnew式と初期化の解説](https://learn.microsoft.com/en-us/cpp/cpp/new-operator-cpp?view=msvc-170)が入口です。

### 「newは必ずmallocを呼ぶ」とは限らない

標準の置換可能なグローバル確保関数を差し替えたり、クラスごとの確保関数を定義したりできます。実装によっては、通常の確保関数がCRTのヒープ管理につながりますが、`new → malloc → OS` という固定の呼出し列がC++で保証されているわけではありません。さらにnew式については、条件を満たす場合に置換可能なグローバル確保関数の呼出しを省略・まとめることも認められます。[確保関数の契約](https://eel.is/c++draft/new.delete.single)と[確保の省略・統合の規則](https://eel.is/c++draft/expr.new#14)を区別して読んでください。

そのため、ソースに書いた `new` の数、確保関数の呼出し回数、OSへの要求回数、実際にアクセスしたページ数は、同じ数になるとは限りません。

## 3. アロケータの中で空きを探す

以下は内部を読むための典型的なモデルです。すべてのアロケータが、この順番や同じデータ構造を採用するわけではありません。

1. **要求を管理単位へ対応させる。** サイズやアラインメントを調べ、扱う大きさの区分へ丸めます。この区分をサイズクラスと呼ぶ実装があります。例えば説明用に「33バイトの要求を48バイトの区分で管理する」と考えると、要求量と内部消費量の違いが見えます。この数値は特定製品の仕様ではありません。
2. **既にある空きを探す。** 空きブロックをつないだフリーリストや、空き状態を表すビットマップなどから、条件を満たす領域を選びます。実装によっては、大きな空きの分割も行います。
3. **スレッド用の領域や共有の管理領域を調べる。** 手元の空きで足りなければ、別の管理領域から補充します。共有データの更新にはロック等の同期が必要になる場合があります。
4. **必要なら下の層へ追加を求める。** 既存領域で満たせなければ、OSなどの供給元から領域を得る、予約済み領域へページを追加でコミットする、といった処理へ進みます。それでも満たせない場合は失敗です。

呼出し元へ返すポインタは、利用してよい領域の先頭です。管理情報をその直前へ置く方式も、別の表から引く方式もあります。**管理情報の配置を推測して、返ったポインタの前後を勝手に読み書きしてはいけません。** アプリケーションが使える範囲と、実装が管理のために保持する範囲を分けます。

### 3種類の「キャッシュ」を区別する

| 名前 | 保存するもの | この話での役割 |
| --- | --- | --- |
| アロケータのスレッド用キャッシュ | 再利用できるブロックなどの管理情報 | 共有の管理領域へのアクセスや同期を減らす |
| CPUのデータキャッシュ | メモリから読んだデータのコピー | 命令による読み書きを速める |
| TLB | アドレス変換に使う情報 | 仮想アドレスから物理アドレスへの変換を助ける |

glibcには、スレッドごとのキャッシュに保持するサイズや個数、管理領域であるarenaなどを調整する仕組みがあります。これは代表例で、固定のしきい値や「常にロック不要」という一般則ではありません。版によって構成も変わるため、[glibcのMemory Allocation Tunables](https://sourceware.org/glibc/manual/latest/html_node/Memory-Allocation-Tunables.html)で対象の版を確認します。

この文脈でのglibcのarenaは、汎用ヒープを管理するための領域です。[一括リセットするアリーナアロケータ](/runtime/memory/allocators-and-pools.html)という使い方と、名前だけで同じ仕組みだと判断しないでください。

小さい確保の多くが再利用で済む実装でも、初回の補充、大きな確保、別スレッドからの解放、管理情報の競合などによって時間は変わります。「汎用ヒープだから必ず遅い」「一回は速かったから毎回一定」とは判断できません。

## 4. OSの確保と、物理RAMに載る時点は別

Windowsの通常のprivate仮想メモリでは、次の状態を分けます。

| 見るもの | 意味 |
| --- | --- |
| 予約（reserve） | アドレス空間の範囲を確保し、ほかの予約に使わせない |
| コミット（commit） | その範囲のページに対して、OSが必要な記憶資源の割当てを管理する |
| 常駐（resident） | 現在そのページが物理メモリに載っている状態 |

`VirtualAlloc` の `MEM_COMMIT` は、要求した全ページへその場で専用の物理ページを割り当て終える、という意味ではありません。通常のページでは、初めてアクセスしたときに必要な物理ページが用意される仕組みがあります。コンストラクタがメンバーへ値を書けば、初期化の時点で既にページへ触れることもあります。[ `VirtualAlloc` の契約](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc)に従って読みます。

この区別から、`malloc` / new式が返るまでの時間だけを計ると、その後の初回アクセスの負荷を見落とすことがあります。初回アクセスに伴うページフォルトも、必ずディスク読出しを意味するわけではありません。[WindowsのWorking Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)と[仮想メモリの本文](/os/virtual-memory.html)で、その先を追えます。

## 5. 失敗したときに、どこまで進んだか

通常の例外を送出する `operator new` は、確保失敗を `std::bad_alloc` で知らせます。`new (std::nothrow) T` では、その確保関数の失敗をnullポインタで受け取れます。ただし、**`nothrow` は `T` のコンストラクタが送出する例外まで抑える指定ではありません。** [単一オブジェクト用の確保・解放関数の契約](https://eel.is/c++draft/new.delete.single)では、nothrow形式のコンストラクタが例外を送出した場合の解放も扱っています。

記憶域取得後の初期化で例外が発生した場合、対応する適切な解放関数が見つかれば、new式は取得済みの記憶域をその関数へ返してから例外を伝えます。通常のnew式ではこの片付けが働きますが、独自のplacement形式などまで無条件に一般化しないでください。完成前のオブジェクト全体のデストラクタを呼ぶ処理とも異なります。規則はC++作業草案の[初期化が例外で終わった場合](https://eel.is/c++draft/expr.new#27)で確認できます。

確保に成功した後も、範囲外アクセスや解放後アクセスが許されるわけではありません。これらは「メモリ不足を扱う処理」とは別の問題です。[メモリバグ図鑑](/runtime/memory/memory-bugs.html)と、[所有権と借用](/runtime/memory/ownership-and-borrowing.html)へつなげます。

## 6. free・delete・OSへの返却を分ける

通常のdelete式はオブジェクトを破棄し、対応する解放関数を使って記憶域を返します。`free` は `malloc` 系で得た領域を返しますが、C++の型固有のデストラクタを呼びません。確保と解放の組合せを守り、`malloc` の結果を `delete` したり、new式の結果を `free` したりしません。`new[]` には `delete[]` が必要です。規則は[ `expr.delete` ](https://eel.is/c++draft/expr.delete)と[CRTの `free` ](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/free?view=msvc-170)を参照してください。

**解放後、アプリケーションはその領域を使う権利を失います。OSへ返ったかどうかは、この禁止を変えません。** アドレスがまだ読めそうに見えても、値が残っていても、再利用される前でも、解放済みのオブジェクトへアクセスしてよい理由にはなりません。`delete p` は変数 `p` を自動でnullにしません。

アロケータは、返されたブロックをキャッシュや空き一覧へ戻し、後の要求に備えられます。隣の空き領域との統合、ページ単位の回収、大きな独立領域の返却などをいつ行うかは実装・設定・要求履歴によります。小さいブロックと同じページに使用中のブロックがあれば、単純にページ全体をOSへ返すこともできません。

WindowsのOS APIでは、[ `VirtualFree` ](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualfree)の `MEM_DECOMMIT` はコミットを解除して予約を残し、`MEM_RELEASE` は予約された領域を解放します。これらは `free` と同じAPIではありません。CRTの `free` の説明にも、OSへ返らなかった空き領域が再確保に使われることが記されています。

したがって、次は別々の観察です。

- **生きている割当てが減ったか**：アプリケーション／アロケータの割当て記録を調べる。
- **プロセスのコミット量が減ったか**：OSが管理する使用量を調べる。
- **ワーキングセットが減ったか**：現在常駐しているページの量を調べる。

使用量のグラフがすぐ下がらないだけでリークと断定できず、下がっただけで所有権や寿命の誤りがないとも言えません。

## 7. ゲームで計測するときの問い

フレーム時間の問題なら、まず「何バイト使っているか」に加え、**確保・解放の回数、サイズ、寿命、発生したスレッド、時間の分布**を記録します。平均だけでなく、ロード直後や初回生成などの遅い回も調べます。

同じサイズを頻繁に出し入れするならプール、同じタイミングで不要になるならアリーナ、表示用オブジェクトを再利用するならObject Pool、という候補が生まれます。ただし、それぞれ保持する余分な容量やリセットの契約があります。詳しい選択は[アロケータとプール](/runtime/memory/allocators-and-pools.html)と[Object Pool](/game/patterns/object-pool.html)へ進めます。

CPUが `new` から戻るまでの時間、コンストラクタで初期化する時間、その後に大量のページを初めて書く時間を、必要に応じて分けて測ります。最適化では「呼出しを減らした結果、どの段階の負荷が減ったか」を確かめます。

## 8. 手元で境界を観察する

[Windows/C++のメモリ観察サンプル](/practice/memory/windows-memory-observation.html)では、OS APIの予約・コミット・初回書込み・解放を分けて観察します。これは `malloc` 内部の全経路を観測するサンプルではありません。**アロケータより下の層の状態変化**を先に確かめ、ヒープの再利用や構築の負荷と区別するための題材です。

記事中の内部経路は説明モデルです。特定のアロケータの回数・しきい値・速度の実測値ではありません。資料の参照確認は2026年11月2日。標準作業草案や実装のマニュアルは更新されるため、利用する言語規格・CRT・OS・ライブラリの版に合わせて確認してください。
