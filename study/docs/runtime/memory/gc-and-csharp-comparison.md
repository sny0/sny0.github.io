# ガベージコレクションとの違い — C#の管理ヒープ・UnityのGC Allocとの比較

## 一言で言うと

**GCは到達できなくなった管理オブジェクトの記憶域を回収し、RAIIはオブジェクトの破棄へ資源の後片付けを結び付けます。** 比べるときは、確保、初期化、破棄、領域の再利用、OSへの返却を別の段階として見ます。

言語名だけで「C#のnewは速い」「C++のnewは遅い」と決めることはできません。サイズ、初期化、確保頻度、生存期間、ランタイム、回収や補充が必要かによって経路が変わります。[malloc/newの内部](/runtime/memory/allocation-journey.html)と[記憶域・寿命](/runtime/memory/storage-duration-and-lifetime.html)へつながる比較です。

## C#の管理ヒープの仕組み(概要)

まず、Microsoftの[.NET GCの説明](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/fundamentals)を前提にします。以下を、すべてのC#実行環境で固定された実装と考えないでください。

1. アプリケーションが管理オブジェクトを作ると、ランタイムが管理ヒープ内の領域を用意し、必要な初期化を行う。
2. 既に用意した領域に空きがあれば、ポインタを進める方式で確保できる場合がある。空き不足や大きな確保では、領域の取得やGCなど別の処理が関係する。
3. GCはスタック上の生存情報、静的な参照、ハンドルなどのルートから到達可能性を調べる。到達できない循環参照も回収対象にできる。
4. 世代別GCは、生存期間の傾向を使い、対象世代を選んで回収する。回収のタイミングと停止時間は、確保量だけから決まるものではない。

圧縮を行う回収では生存オブジェクトが移動する場合があります。ただし、大きなオブジェクトやpinningなども関係するため、**GCがあれば断片化ゼロとは言えません。** オブジェクトが回収された量、GCが保持する領域、プロセスの常駐量も一致するとは限りません。

Unity 6.0のMono/IL2CPPは別に確認します。[GCのモード](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/performance-memory/managed-memory/incremental-garbage-collection)ではBoehm-Demers-Weiser方式と、複数フレームへ処理を分けるインクリメンタルGCを説明しています。これは1回の停止を分割する方針で、GCの総仕事量をなくす機能ではありません。.NETのGen0/1/2や圧縮の挙動を、そのまま当てはめません。Webなど、対応する動作にも差があります。

## コスト構造の対比

| 観点 | C++の典型的なRAII設計 | C#/.NETの管理オブジェクト |
| --- | --- | --- |
| 確保 | 汎用アロケータや用途別アロケータから取得。再利用で済む場合と補充が必要な場合がある | 管理ヒープから取得。既存領域で済む場合と、回収・拡張が関係する場合がある |
| 破棄・後片付け | 所有者の破棄などに結び付ける。デストラクタ内の処理にもコストがある | メモリ回収の時期はGCが管理。ファイル等の後片付けにはDispose/usingなどを使う |
| 保持される領域 | free/delete後もアロケータが再利用用に保持することがある | 回収後もランタイムが管理ヒープの領域を保持することがある |
| 停止や遅延 | 確保、ロック、ページフォルト、大量破棄などを調べる | 確保、初期化、GCの停止や並行処理の負荷などを調べる |
| 参照と所有 | 生ポインタ・参照は通常非所有。unique_ptr等で所有を表せる | GCが見る強い参照と到達可能性が管理オブジェクトの生存に関係する |
| 循環 | shared_ptrだけの強い循環では参照カウントが0にならない | ルートから到達できない循環は回収対象にできる |

どちらも「いつ使わなくなったか」と「誰がその資源を手放すか」を設計します。GCがあっても、イベント購読やstaticなコレクションが不要なオブジェクトを到達可能に保てば、意図せず記憶域を保持します。[Disposeによる資源解放](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/implementing-dispose)はGCの回収とは区別します。

## UnityのGC Alloc対策をC++の語彙で読み直す

| 対策 | 共通する考え方と注意 |
| --- | --- |
| Listやバッファの再利用 | 容量を保持して使い直す。要素数が容量を超える拡張では追加確保が起こり得る |
| Object Pool | 同じインスタンスを再利用する。返却時の状態リセット、参照切断、保持容量も設計する |
| structの利用 | 値型の表現を選ぶ。structにしただけで、常にスタック配置や追加確保ゼロになるわけではない |
| 文字列・クロージャ等の見直し | APIと変換のどこで領域が必要になるかを確認する。C++のラムダも格納先やstd::functionへの変換等で確保が関係し得る |
| NativeArrayなどの利用 | GCが回収する管理領域と、明示的な解放が必要なネイティブ領域を分ける |

UnityのGC.Allocは、管理領域への確保を追うための指標で、OSから取得した量やGCが回収した量ではありません。[Unity 6.0の管理メモリの説明](https://docs.unity.com/en-us/engine/6000.0/manual/analysis/performance-memory/managed-memory/introduction)は、確保の記録、断片化、ヒープ拡張、ネイティブメモリとの違いを説明しています。GC Allocが減っても、保持したプールが大きくなれば総使用量が減るとは限りません。

## C++にGCを入れる選択肢は?

C++で書かれたシステムが、特定のオブジェクト群へGCを使うことはあります。たとえば[UnrealのUObject](/game/unreal/gc-and-object-pointers.html)と、通常のC++オブジェクトの所有関係は分けて読みます。言語、エンジンの管理方式、個々の資源の寿命は同じ分類ではありません。

## Unity開発者が誤解しやすい点

1. **変数のスコープが残れば必ず生存するわけではない。** GCは実行時の生存情報を使います。ネイティブ連携では[GC.KeepAlive](https://learn.microsoft.com/en-us/dotnet/api/system.gc.keepalive)等が必要な場合があり、unsafeやネイティブ領域を安全な管理参照と同じ扱いにはできません。
2. **struct＝スタックではない。** 値型は配列要素やフィールドにもなり、boxingもあります。[C#値型](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/value-types)の値と参照の違いから考えます。
3. **DestroyとGCは別の寿命を扱う。** UnityのC#ラッパーが残ることと、ネイティブ側の実体が生きていることを同一視しません。
4. **GC停止時間と確保時間を分けて測る。** 計測対象、フレーム時間、対象端末、確保サイズ、生存期間をそろえない比較から、言語全体の速さは判断できません。

## 使い分けの視点(まとめ)

まず必要な寿命、保持してよい最大量、フレーム時間の要件を決めます。そのうえで、管理オブジェクトの再利用、RAII、プール、アリーナ等の候補を計測して選びます。小さな一時確保を減らすことと、シーン全体のメモリを解放することでは、見るべき所有者や指標も異なります。

OS側の違いを自分で観察する場合は[Windows/C++の予約・コミット・書込みのサンプル](/practice/memory/windows-memory-observation.html)へ進んでください。このサンプルはGCの停止時間を測るものではありません。

## 理解度チェック

1. GCがオブジェクトを回収しても、常駐量が同じだけ減るとは言えないのはなぜですか。
2. Listの再利用、structへの変更、ネイティブ領域への移動で、それぞれ何を確認しますか。
3. GC、Dispose、UnityのDestroyが扱う対象を区別できますか。

## 演習

自分のプロジェクトの確保を1か所選び、確保量・保持量・回収や破棄の時間を分けて記録します。Unityでは対象バージョンとPlayer/Editor、バックエンド、対象端末、GCモードも記録してください。今回の修正は2026-11-02の一次資料照合であり、これら全環境の性能比較を実行した記録ではありません。
