# メモリレイアウト・パディング・アラインメント・エンディアン

## プロセスのメモリ地図

実行中のプロセスには、コード、データ、ヒープ、各スレッドのスタックなどの領域があります。以下は用途の一覧で、実際のアドレス順・連続性・大きさを表すものではありません。複数のEXE・DLLのイメージ、ヒープ、マップ領域が置かれ、配置はOS・実行ファイル・実行条件等で変わります。[Windowsの仮想アドレス空間](https://learn.microsoft.com/en-us/windows/win32/memory/virtual-address-space)と[プロセス・スレッドの図](/os/process-startup.html)を参照してください。

```
プロセス内にある領域の例（配置順序なし）
├─ 実行イメージ: コード、読み取り専用データ、書き換え可能なデータ等
│  （.text/.data/.rdata/.rodata/.bss等の名前・形式はツールチェーンによる）
├─ ヒープ等: アロケータが管理する領域
├─ スレッドAのユーザースタック・TLS
├─ スレッドBのユーザースタック・TLS
├─ ファイルのマッピング・共有メモリ等
└─ 予約領域・未使用のアドレス範囲等
```

- **スタック**: 通常はスレッドごとに使う領域があります。フレームの調整だけで済む場合もあれば、ページの追加コミットやスタック検査等が関わる場合もあります。予約・コミットの大きさは実行ファイルやスレッド作成の設定で変わり、深い再帰等で[stack overflow](/runtime/memory/memory-bugs.html)に至ることがあります。[Windowsのスタックサイズ](https://learn.microsoft.com/en-us/windows/win32/procthread/thread-stack-size)も参照してください
- **ヒープ**: アロケータの管理下で領域を取得・再利用します。要求できるサイズや保持量には制約があり、取得にも失敗し得ます。[再利用とOSへの追加要求](/runtime/memory/allocation-journey.html)、[断片化](/runtime/memory/allocators-and-pools.html)は別に調べます
- **ページの保護**と**言語上の正しさ**は別です。アクセス違反は不正なアドレスや保護違反の手掛かりですが、範囲外アクセスや解放後アクセスをOSが毎回検出するわけではありません

自動記憶域の変数が必ずスタック上にあるわけではなく、物理RAMへの対応とも別の話です。[記憶域期間と寿命](/runtime/memory/storage-duration-and-lifetime.html)と[仮想メモリ](/os/virtual-memory.html)で区別します。

## アラインメントとパディング

型には**アラインメント（整列）要求**があり、C++では`alignof(T)`で確認します。要求は`sizeof(T)`そのものではありません。例えばサイズが24byteでも整列要求が8byteの型はあります。必要な整列を満たさない場所にその型のオブジェクトを作ることは未定義動作です。コンパイラはメンバーや配列要素の整列を満たすため、構造体に**パディング（詰め物）**を入れることがあります。[C++作業草案の整列規則](https://eel.is/c++draft/basic.align)を参照してください。

```cpp
// C++20、以下のサイズ・offsetは通常のWindows x64設定での例
struct Bad {          // メンバの並びが悪い例
    char a;           // 1バイト  (offset 0)
    // パディング7    (dが8の倍数に置かれるように)
    double d;         // 8バイト  (offset 8)
    char b;           // 1バイト  (offset 16)
    // 末尾パディング7 (配列にしたとき次の要素のdが揃うように)
};                    // sizeof(Bad) == 24

struct Good {         // 大きい順に並べただけ
    double d;         // offset 0
    char a;           // offset 8
    char b;           // offset 9
    // 末尾パディング6
};                    // sizeof(Good) == 16(33%削減)
```

観察用サンプル: <a href="/study/samples/cpp/struct_layout.cpp">samples/struct_layout.cpp</a>（offsetof/sizeofで確認できます。この改訂ではサンプルの再実行は行っていません）

- 実際のサイズとパディングはABI・処理系・設定によって異なります。上記の数値は、例の型と通常のx64設定を前提にします
- 大量に持つ構造体では、並び替えによるパディング削減が保持量を減らす候補になります。速度はアクセス順序やキャッシュ等にも依存するので、サイズだけから決めず計測します（→ [Data Locality](/game/patterns/optimization-patterns.html)）
- `alignas(16)` でSIMD用の16バイト整列を強制、`static_assert(sizeof(Particle) == 32)` でサイズをビルド時固定、が実務の道具
- **バイナリ保存の罠**: 構造体をそのままfwriteすると、パディング(ゴミ)込みで書かれ、コンパイラ/設定が変わると読めなくなる。シリアライズはメンバ単位で

## エンディアン

エンディアンは、複数バイトの値をメモリに置くときの**バイト順**です。下の例はC++20で`std::uint32_t`が提供され、`CHAR_BIT == 8`である環境を前提にします。この条件では`std::uint32_t`は4バイトですが、一般の`int`が常に4バイトとは限りません。[固定幅整数型](https://timsong-cpp.github.io/cppwp/n4861/cstdint.syn)と[C++のバイト](https://timsong-cpp.github.io/cppwp/n4861/intro.memory)を参照してください。

```
std::uint32_t x = 0x12345678; の表現（各欄は16進数2桁）
                      アドレスが小さい側 → 大きい側
リトルエンディアン:    [78] [56] [34] [12]  下位バイトが先
ビッグエンディアン:    [12] [34] [56] [78]  上位バイトが先
```

- バイト内のビットを逆順にする話ではありません。どちらの並びでも、上の値は`0x12345678`です
- **実行環境の表現と、ファイル・通信の形式は別**です。ホストがリトルエンディアンでも、保存先の形式が同じとは限りません。すべてのARM・GPUや通信データを同じ順序と決めつけず、対象の仕様を確認します
- C++20では`<bit>`の`std::endian::native`を`little`や`big`と比較できます。これは実行環境のスカラー型のバイト順を表します。型によって順序が異なる環境などでは、`native`がどちらとも等しくない場合もあります。[C++20草案のエンディアン規定](https://timsong-cpp.github.io/cppwp/n4861/bit.endian)を参照してください

整数の幅・符号・型変換も含めた説明は[ビット・バイト・整数表現](/data/integer-bits-and-bytes.html)へ、実際のバイト列を調べる手順は[整数とバイト列の観察](/practice/data/integer-byte-observation.html)へ進んでください。ここでは、構造体の整列・パディングとバイト順が別の問題であることを押さえます。

## C#との対応

- C#にも構造体レイアウトとパディングは存在する(`[StructLayout]`, `Marshal.SizeOf`)が、通常は意識しない(ランタイムが管理し、フィールド順の再配置すらする)。C++は**書いた順に並ぶ**(標準レイアウト型なら保証)ことが逆に道具になる
- Unityで意識する瞬間: ComputeShaderへの構造体転送、NativeArray、P/Invokeの構造体マーシャリング——このページの知識がそのまま必要になる場面

## Unity開発者が誤解しやすい点

1. 領域の用途、言語上の寿命、ページの保護、確保コストはそれぞれ別の軸です。スタックとヒープの固定的な速度倍率を、この地図から読み取ることはできません
2. 「structのサイズ=メンバの合計」— パディングで増える。順序で変わる
3. 「セーブデータはmemcpyで一発」— パディング・エンディアン・型サイズ(実装定義)の三重の罠

## ゲーム開発での使用例

- パーティクル/コンポーネントのサイズ削減(並び替え、ビットフィールド、量子化)
- SIMD用の `alignas(16)` 整列(→ [SIMD](/runtime/cpp-internals/cache-branch-simd.html))
- ネットワークパケットの明示的レイアウト(固定幅型 `uint32_t`+エンディアン変換)
- クラッシュダンプでアドレスを見て「これはスタック?ヒープ?コード?」を推定する力
