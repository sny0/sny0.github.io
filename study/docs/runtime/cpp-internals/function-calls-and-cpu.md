# 関数呼び出し・コールスタック・呼出規約・レジスタ

## 一言で言うと

通常のx64の関数呼び出しでは、引数を渡し、戻り先を記録して処理を移し、戻り値を受け取ります。引数や戻り値の受渡し、レジスタの保存方法を決める呼出規約は、ABIの一部です。

C++のソース上で関数を呼んだからといって、必ず機械のcall命令が一つ残るわけではありません。インライン展開や末尾呼出しへの変形等もあります。このページでは、通常のユーザーモードのWindows x64と、比較用のSystem V AMD64 ABIを扱います。CPU命令の動作、ABIの取り決め、最適化後の結果を分けて読みます。

## レジスタ — CPUの手元メモリ

レジスタはCPUが命令の実行に使う記憶場所です。x64にはRAX・RCX等の汎用レジスタや、XMM等の浮動小数点・SIMD処理に使うレジスタがあります。命令から見えるレジスタと、CPU内部の物理的な構成は同じ数え方とは限りません。

**レジスタを使う処理だから0サイクル、とは決められません。** 演算結果が使えるまでの遅延、命令を処理する能力、前の命令への依存、実行資源の競合等を考えます。対象CPUに応じた命令のlatencyやthroughputは別々の指標で、[LLVMのllvm-mca](https://llvm.org/docs/CommandGuide/llvm-mca.html)もCPUごとのスケジューリングモデルを使って解析します。その推定を実機の計測と同一視しません。

コンパイラの**レジスタ割付**は、必要な値をどのレジスタ等で保持するか決める処理です。ソースの変数が、そのまま一つの固定した場所に置かれるわけではありません。変数自体が最適化で消えることも、時点によってレジスタとメモリを行き来することもあります。[Debug/Releaseとデバッガ](/tools/build/build-configurations.html)、[記憶域期間と寿命](/runtime/memory/storage-duration-and-lifetime.html)も参照してください。

## 関数呼び出しで起きること(x64の典型)

次は処理の対応を見るためのC++17/20の断片です。示した呼出しでは、計算結果がintの範囲に収まります。

```cpp
int CalcDamage(int atk, int def) {
    int base = atk * 2 - def;
    return base < 1 ? 1 : base;
}
// 呼ぶ側の例：int d = CalcDamage(50, 30);
```

呼出しが残り、通常のWindows x64規約を使う場合は、次のように分けられます。

```text
1. 呼ぶ側が必要な引数・スタック領域を用意
   atk=50をECX、def=30をEDXへ渡す
2. 通常のnear callが、次に戻る命令のアドレスをスタックへ記録
   CalcDamageの処理へ移る
3. 呼び先が、必要ならスタック領域や保存すべきレジスタを準備
4. 本体を実行
5. intの結果をEAXに置き、必要な後片付け・レジスタの復元を行う
6. 通常のretが、スタック上の戻り先へ処理を戻す
7. 呼んだ側が結果を利用する
```

EAXはRAXの下位32ビットを指す名前です。この例のintの値を、必ず64ビット全体の情報として読むわけではありません。float・doubleや構造体は同じ受渡し方とは限りません。以下の規約を確認します。

関数がローカル変数を持つ場合も、必ず毎回スタック領域を広げるとは限りません。最適化、レジスタの利用、ほかの関数を呼ぶか等によって変わります。例外で脱出する場合や末尾呼出しでは、この通常のretまでの流れとは異なる場合があります。

## コールスタックの構造

通常、スレッドごとに実行用のスタックがあり、呼出しに必要な情報を扱います。x64では一般に小さいアドレス側へ伸びます。次の図は説明用で、実際の並び・パディング・引数領域・保存するレジスタをすべて描いたものではありません。

```text
高アドレス側
  mainに関する情報
  main内へ戻るためのアドレス
  Battleに関する情報
  Battle内へ戻るためのアドレス
  CalcDamageに関する情報
低アドレス側へ
```

**スタックトレースは、単にメモリ上の戻り番地を順に探すだけではありません。** Windows x64では、現在の命令位置・レジスタ・スタックと、関数のunwind情報等を使い、呼出し元の状態を復元します。.pdata/.xdataはそのための情報を保持します。PDB等のシンボル・デバッグ情報は、関数名やソース行などを表示する側にも関係します。[Microsoftのx64例外処理とデバッガ支援](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64?view=msvc-170)を参照してください。

フレームポインタを省略しても、適切なunwind情報があれば遡れる構成があります。一方、インライン展開で独立した機械のフレームがなくなったり、末尾呼出しやスタック破壊で期待した形を得られなかったりもします。必要な情報が失われた場合に、シンボルだけで完全に復元できるという保証はありません。

- スタック上の配列からはみ出すと、ほかのデータや制御情報を壊す場合があります。どの情報が壊れるかは配置等によるため、破壊位置を症状だけで決めません。[メモリバグ図鑑](/runtime/memory/memory-bugs.html)で扱います。
- 再帰等で実際にスタックの使用量が増え続け、利用できる範囲を超えるとstack overflowの原因になります。
- スレッドのスタックと、プロセスの仮想アドレス空間の関係は[プロセスの起動](/os/process-startup.html)と[仮想メモリ](/os/virtual-memory.html)へ進んで確認できます。

## 呼出規約 (calling convention)

呼出規約は、**引数・戻り値・保存するレジスタ・スタックの整列等について、呼ぶ側と呼ばれる側が守る取り決め**です。[ABI](/runtime/cpp-internals/symbols-and-linkage.html)の一部で、関数ポインタやネイティブ連携でも一致させる必要があります。

以下は通常の非可変引数の関数で、基本的な整数・ポインタ・float・doubleを渡す場合の比較です。構造体、ベクトル型、可変引数、特殊な規約は別途確認します。

| 観点 | Windows x64の既定の規約 | System V AMD64 ABI |
| --- | --- | --- |
| 整数・ポインタの引数 | 先頭4個の引数位置に応じてRCX/RDX/R8/R9の対応する部分 | 整数用の枠をRDI/RSI/RDX/RCX/R8/R9の順に使用 |
| float・doubleの引数 | 先頭4個の引数位置に応じてXMM0〜XMM3 | 浮動小数点用の枠をXMM0〜XMM7の順に使用 |
| 基本的な戻り値 | intはEAX、ポインタ等はRAX、float・doubleはXMM0 | intはEAX、ポインタ等はRAX、float・doubleはXMM0 |
| スタック側 | 呼ぶ側が4枠分のシャドウスペースを予約。追加の引数等も扱う | スタックへ渡す引数等をABIに従って配置 |

Windowsの「位置に応じる」と、System Vの「型の分類に応じた枠を使う」は違います。例えば宣言が`void Mix(int a, double b, int c);`なら、Windows x64ではa=ECX、b=XMM1、c=R8D、System V AMD64ではa=EDI、b=XMM0、c=ESIという対応になります。

根拠は[Microsoftのx64 calling convention](https://learn.microsoft.com/en-us/cpp/build/x64-calling-convention?view=msvc-170)と、[System V AMD64 psABIの引数・戻り値の規則](https://gitlab.com/x86-psABIs/x86-64-ABI/-/raw/master/x86-64-ABI/low-level-sys-info.tex)です。前者は既定規約、後者はLinux/x86-64等で使うABIの説明で、すべての64ビットCPUや言語内部の呼出しに当てはめる表ではありません。

呼出しの前後で値を残したければ、どのレジスタを呼び先が保存・復元し、どれを変更してよいかも確認します。また、構造体の受渡しは、型の性質やABIによってレジスタへの分割、スタック上の値、隠しポインタ等が使われます。「レジスタに入らない型は常にconst参照が最速」とは判断しません。[C++の渡し方の選択](/design/decisions/cpp-choices.html)へつながります。

32ビットx86の`__cdecl`・`__stdcall`・`__fastcall`等は、32ビット向けコードや既存の連携で引き続き確認が必要です。Windows x64では多くの指定を既定の規約として扱いますが、`__vectorcall`等の別規約もあります。「今は規約が一つなのでヘッダーの指定を無視してよい」とはしません。[Microsoftの規約一覧](https://learn.microsoft.com/en-us/cpp/cpp/argument-passing-and-naming-conventions?view=msvc-170)で対象プラットフォームを確認します。

## 呼び出しのコスト感覚

固定のサイクル数だけで呼出し方を比較することはできません。対象CPU、生成コード、呼出し先の予測、キャッシュ、引数の準備、レジスタの退避、最適化の範囲、呼出し頻度が関係します。

| 呼出し方 | 実際に確認すること |
| --- | --- |
| インライン展開された処理 | 呼出し自体が消えているか。残った計算、コード量、レジスタ使用量はどうか |
| 直接call | 呼出し前後の準備・復元、実行する本体、頻度を含めて測る |
| 仮想関数等の間接呼出し | 呼出し先の予測や、最適化で直接呼出し・インライン展開へ変わる可能性を確認する |
| DLL境界 | インポート等の実際の命令列と、境界を越えて可能な最適化を確認する |
| P/Invoke等の管理・ネイティブ境界 | 遷移、引数の変換・コピー、確保、呼出し頻度と本体を分ける |

**インライン展開でcall命令が消えることと、処理全体が無料になることは別**です。コード量の増加等が不利になる場合もあり、小さい関数でも必ず展開されるわけではありません。コンパイラ、最適化設定、関数の見え方、LTO等の影響を[GCCの最適化オプション](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html)で確認できます。

まず責務に沿って関数を分け、実際に問題となる区間を計測します。分割を戻す、データをまとめて渡す、呼出し回数を減らす等は、原因が分かってから検討します。[早すぎる最適化](/design/foundations/yagni-kiss-dry.html)の話でもあります。ネイティブ連携では、[.NETのinterop指針](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/best-practices)のように、渡す型やマーシャリングの契約も確認します。

## C#との対応

C#のILにある評価用スタックは、中間表現の実行モデルです。機械のコールスタックやC#の`Stack<T>`と同じものではありません。.NETのJITはILをCPU向けコードへ変換し、生成された処理ではレジスタや機械のスタック等を使います。[.NETの管理実行](https://learn.microsoft.com/en-us/dotnet/standard/managed-execution-process)を参照してください。

実行方式はJITだけではありません。[Native AOT](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)や[UnityのIL2CPP](/languages/csharp/il2cpp.html)等、対象環境の生成方式を確認します。管理メソッド同士の内部規約を、ネイティブC++の公開ABIと無条件に同一視しません。

**C#でもスタックトレースが常に完全に取れるわけではありません。** 最適化による変形、デバッグ情報の有無、実行方式等で、見えるメソッドやソース行が変わります。[StackTraceの公式説明](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.stacktrace?view=net-10.0)にも、最適化で期待した数のメソッド呼出しを報告しない可能性が示されています。非同期処理では、論理的な呼出しのつながりと、その瞬間のスレッド上の物理的なスタックも区別します。

## Unity開発者が誤解しやすい点

1. **コールスタックは`Stack<T>`そのものではありません。** 通常のx64の呼出しでは、ABIと生成コードに従って、戻り先、退避したレジスタ、引数や一部のローカル値等を扱います。すべてをpush命令で積むわけではありません。
2. **ローカル変数は必ずメモリ上の固定位置にあるわけではありません。** レジスタへ置く、計算をまとめる、不要として消す等の最適化もあり、デバッガに値が表示されない理由になり得ます。
3. **値渡しが常に遅く、参照渡しが常に速いわけではありません。** 型の大きさ、コピーや参照先へのアクセス、最適化の余地、対象ABIを合わせて考えます。

## ゲーム開発での使用例

- クラッシュ調査では、停止位置、レジスタ、スタック、unwind情報とシンボルの状態を合わせて確認する。トレースが不自然というだけで原因を一つに決めない。
- ホットパスでは、関数の形だけで速度を決めず、生成コードと実測から呼出し回数やデータの渡し方を見直す。
- プラットフォーム移植やプラグイン連携では、引数型、戻り値、呼出規約、保存すべき状態が一致しているか調べる。
- [Windowsのプロセス・スレッド観察例](/practice/process/windows-process-observation.html)でPID/TIDを区別し、スタックがどのスレッドの実行に属するかを意識する。この例だけで各命令のコストを測れるわけではない。

## 理解度チェック

1. ソースに書いた関数呼出しが、そのまま一つのcall命令にならないのはなぜですか。
2. int・doubleを混ぜた引数は、Windows x64とSystem V AMD64でどこへ渡されますか。
3. スタックトレースの復元に使う情報と、その表示が欠ける条件を説明できますか。

## 演習

Compiler Explorer等で、対象のコンパイラ・CPU・ABI・最適化オプションを明示し、`CalcDamage`とその呼出し側の命令を比較します。関数本体だけを見る場合と、呼出し側でのインライン展開を見る場合を分けてください。

引数を変数から受け取る場合と定数の場合、intだけの場合とdoubleを混ぜた場合を比べます。スタック操作やcall命令が残るか、結果が定数になるかは、実際の出力から確かめます。「-O2なら必ずこの形」と決め打ちしません。

本文の対象はC++17/20、通常のWindows x64ユーザーモードの関数呼出し、および比較用のSystem V AMD64 ABIです。C#/.NETとUnityでは実行方式の違いも扱います。2026-11-03に上記一次資料と照合しました。説明用コード・命令列は今回実行しておらず、サイクル数のマイクロベンチマークも行っていません。
