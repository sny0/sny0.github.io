# 第3章 メモリ階層とキャッシュ

## このページで案内すること

メモリ階層、局所性、データ配置を学び、計測で確かめるための**学習計画・概要**です。配置を変えた小さな実験を通じて、計算とメモリアクセスのどちらが制約になっているかを調べます。

## 関連する辞典本文・実践

- [キャッシュ局所性とAoS / SoA](/runtime/memory/cache-locality-aos-soa.html)から、配列の配置とアクセス順を調べられます。
- [キャッシュ・分岐予測・SIMD](/runtime/cpp-internals/cache-branch-simd.html)と[並行処理のバグ・false sharing](/runtime/memory/concurrency-bugs.html)で、CPU側の挙動と計測上の注意を確認できます。

## 学ぶ理由

**メモリアクセスが、ゲーム処理の性能を制約する場合がある。**
メインメモリへのアクセス待ちは、レジスタを使う演算より長くなりやすい。ECS(第15章)も
UnityのDOTS(第16章)も、データ指向設計(DOD)も、すべて
「キャッシュに優しいメモリレイアウト」を実現するための技術である。
この章を理解すると、それらの流行が全部「当然の帰結」に見えるようになる。

## 到達目標

- メモリ階層(レジスタ→L1→L2→L3→DRAM)と各レイテンシの桁を言える
- キャッシュライン(64バイト)・空間局所性・時間局所性を説明できる
- AoSとSoAの違いと、どちらがいつ速いかを説明できる
- 構造体のアラインメントとパディングを図示できる
- false sharing、プリフェッチの概念を説明できる

## 前提知識

第1章(バイト・ビット)、第2章(CPUサイクルの感覚)。

## 学ぶ内容

1. **メモリ階層とレイテンシの桁感覚(数値は説明用の目安)**
   ```
   レジスタ:      命令のオペランド。演算の遅延は命令・CPUに依存
   L1キャッシュ: 約 4 サイクル  (32〜48KB/コア)
   L2キャッシュ: 約 12 サイクル (512KB〜1MB/コア)
   L3キャッシュ: 約 40 サイクル (数十MB共有)
   DRAM:        約 200+ サイクル (数十GB)
   SSD:         数万〜サイクル換算で数百万
   ```
   容量・遅延はCPU/アクセス条件で異なる。DRAM待ちと独立な演算は重ねられるが、
   依存関係や帯域の制約があり、この表から実行時間がそのまま決まるわけではない。
2. **キャッシュの仕組み**
   - キャッシュラインはデータを管理・転送する単位。64バイトは多くのCPUの例で、
     対象CPUの仕様を確認する。同じラインの近隣データを使うと追加の転送を減らしやすい
   - 空間局所性(隣を使え)・時間局所性(すぐまた使え)
   - セットアソシアティブ、エビクション(LRU近似)は概念だけ
   - 書き込み: ライトバック、ダーティライン
3. **データレイアウト設計**
   - **AoS (Array of Structures)**: `struct Enemy{pos, hp, name...}` の配列
     → 1体全体を触るゲームロジック向き
   - **SoA (Structure of Arrays)**: pos[], hp[] を別配列
     → 全体のposだけを走査する物理・カリングで有利になりやすい。実際のアクセスで比較する
   - ホット/コールド分離: 毎フレーム触るデータと稀にしか触らないデータを
     別の構造体に分ける
4. **アラインメントとパディング**
   - 型には整列要件があり、構造体にはパディングが入ることがある。
     `struct{char a; int b;}` が8バイトなのは、intのサイズ/整列が4バイト等の場合の例
   - メンバ並び替えでサイズが縮む実例
   - SIMD型・命令には整列条件がある場合がある。16バイト整列の例は `alignas(16)`。
     floatを4つ並べただけで常に16バイト整列が必須になるわけではない
5. **ポインタ追跡の代償**
   - 連結リスト・`new`で散らばったオブジェクト・仮想関数テーブル参照は
     すべて「ポインタの先へジャンプ」=キャッシュミスの温床
   - 「配列は正義」の定量的根拠
6. **マルチコアとキャッシュ(さわりだけ、詳細は第8章)**
   - コヒーレンシ(MESI)の存在
   - **false sharing**: 別スレッドが同じキャッシュライン上の別変数を
     書くとキャッシュの無効化が増えて遅くなる場合がある。対象のラインサイズを考え、
     共有する必要のないデータを分離して計測する
7. **計測して確かめる**
   - VSの診断ツール、または簡易ベンチマークで「理論を数字で確認」する習慣

## 重要概念

- **「計算は無料、メモリは高い」** ── 現代最適化の第一原理
- **キャッシュライン64バイト** ── データ設計の基本単位
- **局所性** ── 速いプログラムとは局所性の高いプログラム
- **レイアウトはアルゴリズムと同じくらい性能を決める**

## ゲーム開発との関係

| 現場の事象 | この章の知識 |
|---|---|
| ECS/DOTSが「キャッシュフレンドリー」と言われる | SoA・連続配列 |
| `std::vector`推奨、`std::list`はほぼ禁止 | ポインタ追跡の代償 |
| パーティクルを構造体配列で持つ | AoS/SoAの選択 |
| ジョブシステムでスレッド毎にバッファを分ける | false sharing回避 |
| 構造体のメンバ順を変えたらメモリが減った | パディング |
| 「N体の敵AIが重い」→データ再設計で10倍 | データ指向設計 |

## 演習

1. 同じ要素数の `std::vector<int>` と `std::list<int>` の全要素合計を計測し、
   速度差(数倍〜数十倍)を確認せよ。理由をキャッシュラインで説明せよ。
2. 2次元配列の走査を「行優先」「列優先」で計測し、差を確認せよ。
3. 粒子10万個の更新を AoS版とSoA版で書き、位置更新のみ行う場合の
   速度差を計測せよ。
4. `struct A { char c; double d; int i; };` のサイズを予想→`sizeof`で確認
   →メンバ並び替えで最小化せよ。`offsetof`で各メンバ位置も確認。
5. 2スレッドが「隣接するint」をカウントアップするプログラムで
   false sharingを再現し、64Bラインの環境なら `alignas(64)` 等の分離を試して
   計測せよ。CPU・データ配置・使用した整列値を記録する。

## この章がゲームのどこで使われているか

```
1フレームの中身(CPU側)
┌───────────────────────────────────────────────┐
│ 物理更新     : 全剛体の座標配列を走査 → SoAが効く   │
│ アニメ更新   : ボーン行列の連続バッファ             │
│ カリング     : 全オブジェクトのAABB配列を走査        │
│ ECS更新      : コンポーネントを連続配置して一括処理  │
│ 描画コマンド : ソート済み配列を順に舐める            │
└───────────────────────────────────────────────┘
  ▲ 全部「配列をシーケンシャルに舐める」形に設計されている
    = この章のキャッシュ知識が全フレーム処理の設計原理
  ▲ GPUへ送る頂点/定数バッファのレイアウトにも同じ原理(第12章)
```
