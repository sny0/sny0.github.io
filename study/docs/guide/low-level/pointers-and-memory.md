# 第6章 ポインタとメモリ管理

## このページで案内すること

ポインタの読み方から確保・所有・解放へ進み、アロケータやメモリバグを観察するための**学習計画・概要**です。短い概説と演習で調べる順序を決め、個別の規則や実装例は辞典本文へ進んで確認します。

## 関連する辞典本文・実践

- [記憶域期間と寿命](/runtime/memory/storage-duration-and-lifetime.html)、[所有権と借用](/runtime/memory/ownership-and-borrowing.html)で、確保と所有の役割を整理できます。
- [アロケータ・プール・アリーナ](/runtime/memory/allocators-and-pools.html)と[メモリバグ図鑑](/runtime/memory/memory-bugs.html)で、仕組みと失敗例を調べられます。

## 学ぶ理由

メモリ関連の不具合には、ダングリングポインタ、二重解放、バッファオーバーラン、
リーク、断片化などがある。用途に応じて**カスタムアロケータ**(フレーム、
プール、スタックアロケータ)を使うゲームエンジンも多い。
UE5の`FMemory`/`FMallocBinned`や
UnityのNative Allocatorはその具体例だ。この章は「怖くて触れない領域」を
「設計対象」に変える。

## 到達目標

- ポインタに関するあらゆる構文(多重・関数・constの位置)を読み書きできる
- プロセスのメモリレイアウト(スタック/ヒープ/静的/コード)を図示できる
- mallocが内部で何をしているか(フリーリスト等)を説明できる
- スタック/プール/フレームアロケータを自力実装できる
- 代表的なメモリバグ5種を、症状から原因を推測できる

## 前提知識

第3章(メモリ・キャッシュ)、第4章(スタックフレーム)、第5章(C)。

## 学ぶ内容

1. **ポインタの規則と宣言の読み方**
   - ポインタ型は指す先の型をコンパイラに伝える。値は対象等を指すために使い、
     実行時の値に型情報が必ず添付されるわけではない
   - ポインタ演算は要素単位。同じ配列の要素と終端の一つ先までという規則を守る
     (`p+1`が表す要素間の間隔はsizeof(T)。一つ先のポインタは逆参照しない)
   - 多重ポインタ(`T**`は「出力引数」「配列の配列」で頻出)
   - constの位置: `const T*`(このポインタ経由では対象を変更できない)/
     `T* const`(ポインタ自体を変更できない)
   - void*(型消去)とキャスト、関数ポインタ(第5章復習)
   - 宣言の読み方(右左規則): `int (*f[4])(char*)` を読めるように
2. **プロセスのメモリレイアウト(第8章仮想メモリの予告編)**
   ```
   高位 ┌──────────────┐
        │ スタック(下に成長)│ ← ローカル変数・戻り番地
        │      ↓        │
        │   (空き)       │
        │      ↑        │
        │ ヒープ(上に成長) │ ← malloc/new
        ├──────────────┤
        │ .bss/.data     │ ← グローバル・static変数
        ├──────────────┤
        │ .rodata        │ ← 文字列リテラル・定数
        ├──────────────┤
        │ .text          │ ← 機械語(関数の実体)
   低位 └──────────────┘
   ```
   - この図は単純化した配置例。ASLR・複数スレッドのスタック・複数のマッピング等で
     実際の配置は異なる。ヒープが必ず一つの連続領域として上へ伸びるわけではない。
     自動記憶域の変数も必ずスタックにあるわけではない。実際のアドレスとメモリマップを観察する
3. **ヒープの内部構造**
   - 典型的なmallocの実装を「OSから大きな領域を確保し、小分けに配る」モデルで学ぶ。
     OSへの要求方法(VirtualAlloc/mmap等)や管理方式は、処理系・アロケータで異なる
   - フリーリスト、ヘッダ付きチャンク、ビンによるサイズ分類
   - **断片化**(外部断片化)── 長時間動くゲームの宿敵
   - free(p)が領域を識別する管理情報(チャンクのヘッダ等)。配置や検索方法は実装による
4. **カスタムアロケータ(用途に応じた選択)**
   - **リニア/フレームアロケータ**: ポインタを進めるだけ。フレーム末に一括リセット
     → 毎フレームの一時データ(描画コマンド、文字列整形)に最適
   - **スタックアロケータ**: マーカーまで巻き戻せるリニア
   - **プールアロケータ**: 同一サイズ専用。弾・パーティクルに最適。断片化ゼロ
   - **アリーナ**: サブシステム毎に領域を分け、丸ごと解放
   - 実エンジン: UE `FMemStack`/`FMallocBinned2`、Unity `Allocator.Temp/TempJob/Persistent`
5. **メモリバグ図鑑(症状→原因の対応表を作る)**
   - ダングリングポインタ(解放後使用)/二重解放/リーク/
     バッファオーバーラン/未初期化読み/スタック破壊
   - それぞれ「どんなクラッシュ・挙動として現れるか」
   - 検出ツール: ASan(VS/Clangの-fsanitize=address)、VSヒープデバッグ、
     Application Verifier、(UEの)Stompマロケータ
6. **所有権という考え方(C++スマートポインタへの橋)**
   - 「誰がfreeする責任を持つか」を型と規約で表す
   - 生ポインタ=非所有の参照、という現代の慣習

## 重要概念

- **ポインタは「型付きアドレス」**。恐れる対象ではなく計算対象
- **確保と解放の対称性・所有権**
- **汎用アロケータは万能ゆえに遅い** → 用途特化アロケータが速い
- **寿命でメモリを設計する**(フレーム寿命/レベル寿命/永続)── エンジン設計の核

## ゲーム開発との関係

| 現場の事象 | この章の知識 |
|---|---|
| ヒットストップ中の不定期スパイク | mallocのコスト・断片化 |
| 「毎フレームnewするな」ルール | フレームアロケータの思想 |
| 弾・パーティクルのプール運用 | プールアロケータ |
| 長時間プレイでのメモリ枯渇 | リーク・断片化 |
| 稀に飛ぶ「Access Violation 0xdddddddd」 | 解放後使用(VSのフィルパターン) |
| UEのFMemStack/Unity Allocator.Temp | この章の技術そのもの |

## 演習

1. スタック・ヒープ・static・コード(関数アドレス)のアドレスを表示し、
   自分のプロセスのメモリマップを描け。
2. **malloc自作**: 固定長バッファ上にヘッダ+フリーリスト方式の
   my_malloc/my_freeを実装せよ(結合処理は簡易でよい)。
3. **フレームアロケータ**を実装し、毎フレームreset()する使い方で
   1万回のmalloc/freeと速度比較せよ。
4. **プールアロケータ**を実装し、パーティクル1万個の生成破棄を回せ。
5. VSのデバッグヒープで、未初期化(0xCD)・解放済み(0xDD)・
   ガード(0xFD)のフィルパターンをメモリウィンドウで確認せよ。
6. ASanを有効化し、わざと書いた解放後使用・範囲外書き込みが
   どう報告されるか確認せよ。

## この章がゲームのどこで使われているか

```
1フレームのメモリ活動
┌────────────────────────────────────────────────┐
│ 入力処理    : (確保なし ← それが正しい)            │
│ ゲーム更新  : 弾生成→プールから取得(mallocしない)  │
│              一時計算→フレームアロケータ           │
│ 描画       : コマンドバッファ→フレームアロケータ    │
│ フレーム末  : フレームアロケータをreset(一括解放)    │
├────────────────────────────────────────────────┤
│ レベルロード時: レベルアリーナに大量確保             │
│ レベル終了時 : アリーナ丸ごと解放(リーク原理的にゼロ) │
└────────────────────────────────────────────────┘
UE: FMemStack/FMallocBinned2  Unity: Allocator.Temp/TempJob/Persistent
= この章で作ったものの産業版
```
