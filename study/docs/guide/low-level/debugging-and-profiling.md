# 第18章 デバッグとプロファイリング ── 全レイヤを「見る」技術

## 学ぶ理由

ここまでの章で「システムがどう動くか」を学んだ。この章は
「動いている実物を観測する技術」だ。トッププログラマとそれ以外を
分けるのは、書く速度ではなく**原因特定の速度**である。
そして最適化の鉄則はただ一つ ──「推測するな、計測せよ」。
計測できない人の最適化は迷信であり、AI生成コードのレビュー
(最終目標のひとつ)も、検証手段を持つ人だけが本当にできる。

## 到達目標

- VSデバッガを完全に使いこなせる(条件付きBP、データBP、ダンプ解析、
  リリースビルドデバッグ、逆アセンブリ併読)
- クラッシュの4大類型を症状から切り分けられる
- CPUプロファイラ(VS/Tracy/Superluminal/Unreal Insights)で
  ホットスポットとスパイクを特定できる
- GPUプロファイラ(RenderDoc/PIX)でGPUフレームを分解できる
- 「CPUバウンドかGPUバウンドか」から始まる系統的な最適化手順を実践できる

## 前提知識

全章(特に第4章アセンブリ、第6章メモリ、第8章スレッド、第11〜13章GPU)。

## 学ぶ内容

1. **Visual Studioデバッガ 完全習得**
   - ブレークポイント術: 条件付き、ヒットカウント、**データブレーク
     ポイント(このアドレスに書いたら停止 ── メモリ破壊犯の現行犯逮捕)**、
     関数BP、トレースポイント
   - ウォッチ/メモリ/レジスタ/逆アセンブリ/並列スタックウィンドウ
   - Edit and Continue、Natvis(TArray等を見やすく ── UE標準装備)
   - **リリースビルドのデバッグ**(最適化との付き合い方、第4章の実戦)
   - リモートデバッグ、アタッチ
2. **クラッシュ解析**
   - クラッシュ4大類型と初動:
     (a) Access Violation → アドレスを見る(0近傍=ヌルポ、
     0xdd..=解放済み、0xcd..=未初期化 ← 第6章回収)
     (b) スタックオーバーフロー (c) 純粋仮想呼び出し/vtable破壊
     (d) ヒープ破壊(壊れた場所≠壊した場所 → データBP・ASan・PageHeap)
   - **ミニダンプ解析**: WinDbg/VSでダンプを開き、!analyze、
     コールスタック・レジスタから原因推定(QAから来るダンプの読み方)
   - シンボル(PDB)の仕組みとシンボルサーバ(第7章の回収)
   - assert文化・ログ設計(再現困難バグへの備え)
3. **CPUプロファイリング**
   - 2方式の理解: **サンプリング**(統計的・全体像)と
     **インストルメンテーション**(区間計測・スパイク向き)
   - VS診断ツール、**Tracy**(ゲーム向き・無料・フレーム軸表示)、
     Superluminal、Unreal Insights / Unity Profiler
   - 読み方: セルフ時間vs包括時間、ホットパス、**平均ではなく
     最悪フレーム(スパイク)を見る**(ゲームは99パーセンタイルが体感)
   - マルチスレッドの観察: どのコアが遊んでいるか、ロック待ち、
     ジョブの隙間(第8章の実戦)
   - メモリプロファイリング: リーク検出、確保頻度、断片化
4. **GPUプロファイリングとデバッグ**
   - **切り分けの第一歩: CPUバウンドかGPUバウンドか**
     (GPU使用率・stat unit・フレーム時間の挙動で判定)
   - **RenderDoc**: フレームキャプチャ→イベント順に描画を再生→
     ステート検査→ピクセル履歴→シェーダデバッグ。
     「絵が出ない/おかしい」系の必須ツール
   - **PIX on Windows**: GPU時間の計測(オキュパンシ、各パスのms)、
     タイムライン ──「どのパスが重いか」系の必須ツール
   - GPUバウンドの内訳分解: 頂点/ピクセル/帯域/固定機能
     (解像度を下げて速くなればピクセル系、など切り分けヒューリスティクス)
   - デバイスロスト/GPUクラッシュ(TDR)、Aftermath/DRED(概要)
5. **系統的最適化プロセス(この章の総まとめ)**
   ```
   1. 計測して現状把握(フレーム時間分布・スパイク頻度)
   2. CPU / GPU どちらがボトルネックか
   3. その中のどのシステム/パスか(プロファイラ)
   4. なぜ遅いか(アルゴリズム? キャッシュ? 同期待ち? 帯域?)
   5. 仮説→修正→再計測(1つずつ! 同時に2つ変えない)
   ```
   - 最適化の優先順位: アルゴリズム/データ構造 → データレイアウト →
     並列化 → マイクロ最適化(この順で費用対効果が高い)
6. **AIコードレビューへの応用(最終目標の回収)**
   - AI生成コードの典型的問題パターン集:
     毎フレーム確保、隠れたコピー(値渡しstring/vector)、O(n²)、
     スレッド安全性の欠如、例外前提設計、キャッシュ敵対的レイアウト、
     「動くが計測していない」最適化
   - レビュー手順: 正しさ(UB・境界・所有権)→ 性能(計測)→ 設計(依存方向)

## 重要概念

- **推測するな、計測せよ** ── 本章の、そして最適化のすべて
- **データブレークポイント** ── メモリ破壊バグの最終兵器
- **平均でなく最悪フレーム** ── ゲーム特有の品質基準
- **ボトルネックの階層的切り分け**(CPU/GPU→システム→原因)
- **観測手段を持つ者だけが「理解した」と言える**

## ゲーム開発との関係

この章は「関係」ではなく日常業務そのもの。QAのクラッシュレポート対応、
最適化週間、絵が出ないバグ、フレーム落ち調査 ── 全部この章である。

## 演習

1. わざと作ったメモリ破壊バグ(範囲外書き込みで隣の変数を壊す)を、
   データブレークポイントで犯人特定せよ。
2. クラッシュするプログラムのミニダンプを自動保存する仕組み
   (SetUnhandledExceptionFilter+MiniDumpWriteDump)を自作ゲームに
   組み込み、ダンプをWinDbg/VSで開いて原因を特定せよ。
3. 第15章の自作エンジンに**Tracy**を組み込み、ゾーンマーカーで
   フレーム内訳を可視化せよ。意図的なスパイク(たまにsleep)を仕込み、
   プロファイラで発見する練習をせよ。
4. 自作エンジンの敵1万体シーンで最適化プロセスを一周せよ:
   計測→ボトルネック特定→仮説→修正→再計測をレポートにまとめる。
5. RenderDocで「テクスチャが真っ黒になるバグ」(自分で仕込む:
   サンプラ設定ミス等)を特定せよ。ピクセル履歴を使うこと。
6. PIXで自作/サンプルD3D12アプリのGPUタイムラインを取り、
   最も重いパスを特定→解像度スケールで仮説検証せよ。
7. AIに「パーティクルシステムを書いて」と頼み、生成コードを
   本章のレビュー手順で査読し、問題点を列挙→計測で裏取りせよ。
