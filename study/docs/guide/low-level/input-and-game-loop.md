# 第14章 入力とゲームループ ── パッドの旅とフレームの解剖学

## 学ぶ理由

ゲームループはゲームプログラムの心臓であり、この教本の題名
「ボタンを押してから画面に出るまで」の**背骨**である。
可変フレームレートの罠、固定タイムステップ、入力遅延、VSync ──
これらは「格ゲーで1F単位の入力が成立する理由」「物理が低fpsで
すり抜ける理由」に直結する、極めて実務的な知識だ。

## 到達目標

- Win32メッセージループとゲームループの関係を説明できる
- XInput/GameInputでパッド入力を取得し、エッジ検出(押した瞬間)を実装できる
- 可変Δt・固定タイムステップ・補間描画を実装し使い分けられる
- 入力遅延の内訳(パッド→OS→ループ→GPU→表示)を定量的に説明できる
- ゲームループ+入力+描画の「最小のゲーム」をエンジンなしで書ける

## 前提知識

第8章(OS・入力経路・タイマ)、第13章(スワップチェーン・Present)。

## 学ぶ内容

1. **ウィンドウとメッセージループ(Windows)**
   - WinMain、ウィンドウプロシージャ、WM_INPUT/WM_KEYDOWN
   - PeekMessage(ゲーム式)とGetMessage(GUI式)の違い
   - 「応答なし」の正体(メッセージを汲まないウィンドウ)
2. **入力の取得**
   - パッド: XInput(簡単・Xbox系)/ GameInput(新世代)/ RawInput /
     DirectInput(旧)/ SDLやengineの抽象化層
   - **ポーリング型**(毎フレーム状態取得)と**イベント型**の整理
   - エッジ検出: pressed = now & ~prev(ビット演算! 第1章の回収)
   - 入力バッファリング(先行入力)、デッドゾーン処理(円形/軸別)
   - キーコンフィグ層の設計(物理入力→論理アクションの写像)
3. **時間の計測**
   - QueryPerformanceCounter、単調クロック、doubleの蓄積誤差(第1章回収)
   - Δt(デルタタイム)の計測とクランプ(デバッガ停止後の暴走防止)
4. **ゲームループの類型(この章の核心)**
   - (a) 可変Δt: シンプルだが刻み幅で数値積分や衝突結果が変わりやすく、
     大きなΔtでは不安定化やすり抜けの原因になる。可変というだけで非決定とは限らない
   - (b) **固定タイムステップ+可変描画(accumulator方式)**:
     `while (acc >= FIXED_DT) { Update(FIXED_DT); acc -= FIXED_DT; }`
     +残余で**補間描画** ── 「Fix Your Timestep!」(Glenn Fiedler)の定番
   - (c) 完全固定(格ゲー・レトロ等): 同じ刻みで進めることは再現性の土台。
     固定Δtだけでは決定性は保証されず、初期状態・入力を適用するstep・乱数列・
     更新順・並列処理・浮動小数点設定等も揃えて検証する
   - エンジンの実際: UnityのUpdate/FixedUpdate、UEのTickと物理Substepping。
     更新周期や補間の方式はエンジン/設定ごとに確認し、両者を同一のループと決め付けない
5. **フレームペーシングと表示**
   - VSync、ティアリング、可変リフレッシュ(G-Sync/FreeSync)
   - フレームペーシング(一定間隔でPresentする工夫)とマイクロスタッター
   - **入力遅延の全内訳(この教本の主題の縦断面)**:
     パッドスキャン(〜8ms) + USBポーリング(〜1ms) + OS/ドライバ +
     入力サンプリングのタイミング + ゲーム更新(1F) +
     GPUレンダリング(1F) + フレームインフライト(0〜2F) +
     ディスプレイのスキャンアウト/応答(〜数ms)
     各値は説明用の例。処理の重なり・キュー・画面上の位置・機器設定によって
     合計は変わり、30〜80ms等の範囲が全環境に当てはまるわけではない。
     遅延フレーム削減等の技術が、どの待ち時間を減らすかを考える
6. **メインループの周辺設計**
   - 更新順序(入力→AI→物理→アニメ→カメラ→描画)とその理由
   - ポーズ・スローモーション(タイムスケール)、決定性とリプレイ

## 重要概念

- **ゲームは「毎フレーム世界を作り直す」シミュレーション**
- **エッジ検出** ── 「押している」と「押した瞬間」の区別
- **固定タイムステップ+補間** ── 物理の安定と映像の滑らかさの両立
- **入力遅延はシステム全体の和** ── 1箇所の最適化では消えない
- **決定性** ── 同じ初期状態と入力列から同じ状態列を得る性質。時間刻みの列を含めて実装と実行条件を揃え、比較して確かめる

## ゲーム開発との関係

| 現場の事象 | この章の知識 |
|---|---|
| UnityのUpdateとFixedUpdateの違い | ループ類型(b) |
| 高速移動で壁抜けする | 可変Δt物理・サブステップ |
| 格ゲーの1F入力・先行入力 | ポーリング周期・入力バッファ |
| 「60fpsなのにカクつく」 | フレームペーシング・マイクロスタッター |
| リプレイのズレ | 決定性・浮動小数・乱数 |
| デバッガで止めた後に物理が爆発 | Δtクランプ |

## 演習

**この章の演習が「自作ミニエンジン」の第1マイルストーンになる。**

1. Win32+第13章のレンダラ(またはSDL)で:ウィンドウ+ゲームループ+
   XInputで四角形を動かす「最小のゲーム」を書け。エンジン不使用。
2. エッジ検出・デッドゾーン(円形)・先行入力バッファ(10F)を実装せよ。
3. 同じ「重力でジャンプするボール」を (a)可変Δt (b)固定タイムステップ+
   補間 で実装し、120Hz/30Hz環境(疑似的にSleepで)での挙動差を観察せよ。
4. パッドを押した瞬間に画面を白フラッシュさせ、240fpsスマホカメラで
   撮影して自作ループの入力遅延を実測せよ(現場でも使う手法)。
5. 「入力→更新→描画」の各時間をQueryPerformanceCounterで計測し、
   画面にオーバーレイ表示せよ(自作プロファイラの種、第18章へ)。
6. ブロック崩しを完成させよ(タイトル→プレイ→ゲームオーバーの
   状態遷移含む)。ここまでの全章が総動員される。

## この章がゲームのどこで使われているか

```
この章 = 教本タイトルの背骨そのもの
────────────────────────────────────────────────
パッド押下 ──(第8章の経路)──→ OSに入力到達
                                  │
      ┌── ゲームループ(毎フレーム)◄┘
      │ ① 入力ポーリング ← XInputGetState (押した瞬間を検出)
      │ ② 固定タイムステップ更新 × N回 (物理・ゲームロジック)
      │ ③ 補間係数を計算して描画コマンド生成 (第15章のエンジン仕事)
      │ ④ Present (第13章スワップチェーン)
      └──── 16.6ms で1周 ────→ 数フレーム後、光として画面に
────────────────────────────────────────────────
Unity: PlayerLoop / UE: FEngineLoop::Tick = この図の産業版
```
