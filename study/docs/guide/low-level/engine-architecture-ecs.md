# 第15章 ゲームエンジンの構成とECS

## このページで案内すること

エンジンを構成する責務とデータの流れを整理し、小さな構成で試すための**学習計画・概要**です。ECSは構成方法の一つとして学び、規模や用途に合わせて他の設計とも比較します。

## 関連する辞典本文・実践

- [ゲームエンジンの役割](/game/basics/game-engine-basics.html)と[シーンとコンポーネント](/game/basics/scenes-and-components.html)で、機能と配置の基本を確認できます。
- [責務と関心の分離](/design/foundations/responsibility-and-separation.html)で、構成を分ける根拠を確認できます。
- [ECS](/game/ecs.html)と[Componentとの比較](/game/patterns/component-and-ecs.html)で、データ配置・Query・構成変更を調べられます。
- [実行時のアセットロード](/game/asset-loading.html)で読取り完了とReady、登録・所有権・解放を分け、[状態と寿命の実践](/practice/assets/asset-lifecycle-model.html)で世代を含むモデルを確かめられます。実践は単一スレッドの決定的なコンソール例で、実ファイルI/O、ワーカー、GPU、Unityは扱いません。
- 読取り方式の違いは[ファイルread](/os/file-read-journey.html)、[非同期I/O](/os/asynchronous-file-io.html)、[メモリマップドファイル](/os/memory-mapped-files.html)へ進みます。マッピングの範囲と寿命は[専用の観察例](/practice/io/mapped-file-observation.html)で確認できます。

## 学ぶ理由

ここまでの全章は部品だった。この章で部品を「エンジン」に組み上げる。
エンジンの層構造・ゲームオブジェクトモデル・アセットパイプライン・
シーン管理を一般論として理解しておくと、次章以降のUnity/UEが
「同じ問題への2つの解答例」として読めるようになる。そしてECSは、
第3章(キャッシュ)・第9章(仮想関数のコスト)の知識が結晶した
現代の設計様式である。

## 到達目標

- エンジンのレイヤ構造(プラットフォーム→コア→リソース→シーン→ゲーム)を描ける
- ゲームオブジェクトモデル3類型(継承/コンポーネント/ECS)の得失を説明できる
- アーキタイプ型とスパースセット型ECSの内部実装を説明できる
- アセットパイプライン(インポート→クック→ロード)の役割を説明できる
- 実行時ロードの読取り・デコード・登録・利用可能化と、要求の世代・資源の所有・解放を分けて説明できる
- 数千行規模の「ミニエンジン」を自力で設計・実装できる

## 前提知識

第3,6,9,10章(キャッシュ・アロケータ・C++・データ構造)、
第12〜14章(レンダリング・API・ループ)。

## 学ぶ内容

1. **エンジンのレイヤ構造(Gregory本の地図)**
   ```
   ゲーム固有コード(タイトル側)
   ─────────────────────────────
   ゲームプレイ基盤(オブジェクトモデル・イベント・スクリプト)
   シーン/ワールド(シーングラフ・空間分割・ストリーミング)
   機能システム(レンダラ/物理/アニメ/オーディオ/UI/AI)
   リソース管理(アセットロード・参照解決・キャッシュ)
   コア(数学・コンテナ・アロケータ・ジョブ・ログ・シリアライズ)
   プラットフォーム抽象(ウィンドウ・入力・ファイル・スレッド・RHI)
   ─────────────────────────────
   OS / ドライバ / ハードウェア(第2〜13章)
   ```
   - 依存は必ず下向き。上位層は下位層を知るが逆は禁止
2. **ゲームオブジェクトモデル(エンジン設計の中心問題)**
   - (a) 継承ベース: `Enemy : Character : Actor`(初期UEの姿)
     → ひし形・神クラス・柔軟性欠如で破綻しがち
   - (b) コンポーネント指向: GameObjectにComponentを刺す(Unity/現UE)
     → 合成による柔軟性。だがポインタだらけでキャッシュに不利
   - (c) **ECS**: Entity=ただのID、Component=純データ、System=処理
     → データ指向の帰結。UnityのDOTS、Overwatch等
3. **ECSの内部実装(2大流派)**
   - **アーキタイプ型**(Unity DOTS, flecs): 同じコンポーネント構成の
     エンティティを同じ「テーブル」に連続配置。イテレーションが爆速、
     構成変更(add/remove)が高い
   - **スパースセット型**(EnTT): コンポーネント毎に密配列+疎な索引。
     add/removeが速い、複数コンポーネント横断はやや劣る
   - generation付きEntityID(第10章ハンドルの回収)
   - どちらも本質は「第3章のキャッシュ理論の応用」であること
4. **リソース/アセットパイプライン**
   - ソースアセット(FBX/PNG)→インポート→中間形式→**クック**
     (プラットフォーム別最適形式)→パッケージ→実行時ロード
   - 参照の表現(GUID/パス)、依存グラフ、ホットリロード
   - 実行時: 読取り→展開/デコード→登録・転送→Readyを分ける。必要な段階はアセットの種類とAPIで異なり、I/O完了だけではReadyにならない。[アセットロードの本文](/game/asset-loading.html)へ
   - 登録を行えるスレッドは対象APIの契約に従う。例えば多くのUnity APIはメインスレッドから呼ぶ必要があり、バックグラウンド処理の終了だけでは呼出し条件を満たさない。[Unity: 完了と継続](https://docs.unity.com/en-us/engine/6000.0/manual/scripting/optimization/async-await-support/async-awaitable-continuations)
   - 参照数は所有の管理に使うが、GPUが参照中の資源を即時解放できるとは限らない。例えばD3D12では使用を含むGPU処理の完了をフェンスで追跡する。[Microsoft: Fence-Based Resource Management](https://learn.microsoft.com/en-us/windows/win32/direct3d12/fence-based-resource-management)
   - ストリーミング(距離ベース、UEのWorld Partitionなど)。要求の世代と所有権を保ち、古いロード結果を新しい要求の結果として登録しない設計を学ぶ
5. **フレームの全体オーケストレーション**
   - システム更新順序、フェーズ(入力→ゲーム→物理→アニメ→
     カメラ→カリング→描画コマンド→提出)
   - ジョブグラフ化(第8章ジョブシステムの回収)、
     メインスレッド/レンダースレッド分離(UEの構造の先取り)
   - イベント/メッセージング(即時 vs キュー、フレーム跨ぎ)
6. **周辺システムの概観(深入りは各専門書)**
   - 物理(broadphase=第10章空間分割、narrowphase、ソルバ)
   - アニメ(スケルトン、ブレンド、ステートマシン)
   - オーディオ(ミキサ、レイテンシ ← リングバッファの実用)
   - UI(イミディエイト vs リテイン、Dear ImGuiの思想)
   - シリアライズ(セーブ・シーンファイル・リフレクションの必要性 ← UEへ伏線)
7. **ミニエンジンを作る(本教本最大の演習)**

## 重要概念

- **レイヤと依存方向** ── 大規模ソフトの背骨
- **合成 > 継承** ── ゲームオブジェクト設計の歴史的教訓
- **ECS = ID + 連続データ + 一括処理**(キャッシュ理論の結晶)
- **アセットは「ビルドされる」**(クックという概念)
- **エンジンとは「毎フレームの決まった仕事の工場」**

## ゲーム開発との関係

| 現場の事象 | この章の知識 |
|---|---|
| UnityのGameObject/Component | モデル(b)の実装 |
| UEのActor/ActorComponent | (a)+(b)のハイブリッド |
| Unity DOTS / Mass Entity(UE) | ECS |
| アセットのインポート待ち・クック | アセットパイプライン |
| 「Updateの順序が保証されない」問題 | システム更新順序設計 |
| オープンワールドのストリーミング | リソース管理・World Partition |

## 演習

**ミニエンジン制作(2Dで十分。3Dは意欲があれば)**

1. 設計: レイヤ図とモジュール一覧を先に紙に描け(コア/プラットフォーム/
   レンダラ/リソース/シーン/ゲーム)。
2. コア層: 数学(第10章の自作品)、フレームアロケータ(第6章の自作品)、
   ログ、アサートを整備せよ。
3. **スパースセット型ECSを自作せよ**(entity生成破棄、component
   add/remove/get、view(複数component横断イテレーション)。500行程度)。
4. システム: MovementSystem、CollisionSystem(グリッド)、
   RenderSystem(スプライトバッチング)を実装せよ。
5. リソース: まず[状態と寿命のモデル](/practice/assets/asset-lifecycle-model.html)で、成功・失敗・古い世代の結果・解放を確かめよ。その後、テクスチャ/サウンドのキャッシュ付きローダを実装し、参照数、登録スレッド、GPU使用完了など、対象APIに応じた解放条件を決めよ。
6. これらで**小ゲームを1本完成させよ**(シューティングや
   Vampire Survivors風など、物量が出るものがECSの真価を示す)。
7. 敵1万体を出し、(第18章の道具で)プロファイルして
   ボトルネックを1つ潰せ。
8. 自作ECSとEnTTで同じ処理を書き、速度と設計を比較せよ。

## この章がゲームのどこで使われているか

```
1フレーム = エンジンという工場のベルトコンベア
────────────────────────────────────────────────
[入力] → [ゲームシステム群の更新(ECS: 連続データを一括処理)]
       → [物理(グリッド/BVH→解決)] → [アニメ(ボーン行列)]
       → [カメラ] → [カリング] → [描画コマンド生成(ソート)]
       → [RHI提出(第13章)] → [Present]
  ↑ この工程表・部品配置・メモリ計画を設計するのがエンジン設計
  ↑ Unity/UEは この図の巨大産業版(次の2章で内部を見る)
アセット: FBX/PNG →(クック)→ 最適バイナリ → 読取 → 展開/デコード
          → 登録・転送 → 利用可能(Ready。必要な段階は種類・APIによる)
```
