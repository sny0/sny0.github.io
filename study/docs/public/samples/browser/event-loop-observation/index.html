JavaScript / Browser event loop

予約した順と、
実行された順を比べる

各ケースの予測を読んでから実行し、下のログで確かめます。Promise・await・timer・rAFを、有限の小さな処理で見比べる実験です。

CASE A

同期・Promise・await

Promiseのexecutorと、async関数のawaitより前は、呼出し中に実行されます。

このケースの予測順を見る
  1. sync:start
  2. Promise:executor
  3. async:before-await
  4. sync:end
  5. Promise:then
  6. queueMicrotask
  7. async:after-await
  8. timer:0ms

CASE B

途中で追加するmicrotask

microtaskの中で次のmicrotaskを予約します。3つ実行したあとにtimerへ進みます。

このケースの予測順を見る
  1. sync:start
  2. sync:end
  3. microtask:1
  4. microtask:2
  5. microtask:3
  6. timer:0ms

CASE C

rAFとtimerを比べる

Promise・rAF・timerを予約します。コード上の予約順だけで、rAFとtimerの相対順は決めません。

固定する部分と観察する部分を見る
  1. sync:start
  2. sync:end
  3. Promise:then

この後のrAF:callbackとtimer:0msは実際の順を観察します。両方が終わるまで実行中です。

    観察するときの注意

    setTimeout(..., 0)は、その行でcallbackを即実行する指定ではありません。rAFは描画の更新に関係するcallbackで、独立した「万能FIFO task queue」に全部を並べるモデルでは説明しません。

    非表示のタブではrAFが遅延・抑制され得ます。ケースCが待機したままならタブを表示するか、初期化してください。初期化は常時使え、timerとrAFを取り消し、古い世代のmicrotaskからの記録も無視します。

    外部依存、fetch、storage、analyticsはありません。無限のmicrotask連鎖、busy loop、毎フレームのループは実行しません。ログを表示するDOM更新も処理の一部です。
