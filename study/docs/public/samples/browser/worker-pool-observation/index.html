Worker pool / FIFO / Backpressure

実行2件、待機4件。
7件目はどうする？

固定2つのWorkerへ一件ずつ送ります。待機枠が満杯なら新しい要求を拒否し、待機の取消しと実行中の結果破棄を区別する実験です。

1. 起動して、7件をまとめて依頼する

HTTPまたはHTTPSで、ページと外部worker.jsを同じoriginから配信してください。

状態：停止

2つのreadyを受け取ってから、要求を受け付けます。

カウンター：0 次の要求ID：1（初期化でも再利用しません）

一括依頼はまだ実行していません。

2. 実行枠と待機枠を見る

workerは16値の合計120と件数16を求め、timerへ3000msを指定して返信します。CPU性能を比較する処理ではありません。実行中に結果破棄を指定しても、返信を受けるまで実行枠は空けません。

accepted = running + waiting + completed + queuedCancelled + discarded + aborted

不変条件：0 = 0

結果破棄待ちはrunningの中です。rejectedはacceptedの外です。表示履歴を整理しても集計は残し、「停止して初期化」で集計・履歴を消します。

要求の状態

未完了の全件と、終端に達した最新20件だけを表示します。FIFOは待機から送る順序で、異なるworkerの完了順を固定するものではありません。

要求IDはページの生存中に再利用しません
ID状態slot / 補足採用結果
要求はまだありません。

操作と通信のログ 最新60件

時刻はmainが記録したperformance.now()です。paint完了やCPU処理時間ではありません。

    取消し・破棄・停止の違い

    待機取消しは未送信の要求をqueueから除きます。実行中の結果破棄は仕事を止めず、結果を回収してから枠を空けます。pool停止は全workerをterminateし、待機と実行中をabortedにします。自動retryはありません。

    ready待ちは各workerに8秒、ジョブはdispatch時から8秒のsoft timeoutです。queueの待機期限は設けません。背景タブ等ではtimerが遅延し得るため、厳密な実時間の保証ではありません。

    外部ライブラリ、fetch、storage、analytics、アニメーション、busy loopは使いません。file://では起動せず、HTTP(s)で同じoriginから配信する構成です。
