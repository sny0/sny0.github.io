# バイナリファイルの読み取り前に範囲を検査する

ゲームがパックファイルからアセットを読むとき、最初に読むのは索引です。索引に「先頭から60バイトの位置に、4バイトのデータがある」と書かれていれば、その範囲を取り出します。更新途中のファイルや壊れたファイルでは、同じ欄がファイルの末尾を指し越すこともあります。件数や長さは、対応する範囲を確かめてからメモリ確保や読み取りに使います。[ゲームのアセットパック](/game/asset-pack-files.html) · [ファイル読み取りと短い読み取り](/os/file-read-journey.html)

## 最小のヘッダーから読む

実践用の`SPAK`形式は4バイトの識別子`SPAK`、4バイトのバージョン、4バイトの件数から始まります。その後に24バイトの索引項目が件数分並びます。各項目はNULで埋めた16バイトのASCII名、4バイトのオフセット、4バイトの長さで構成します。数値欄は符号なし32ビットのリトルエンディアンで、オフセットはファイルの先頭から数えます。[C++の固定幅整数型](https://eel.is/c++draft/cstdint.syn) · [整数とバイト列の読み方](/data/integer-bits-and-bytes.html)

まず12バイトが存在することを確かめ、識別子を照合します。次に版を確認し、その版が定める位置・幅・バイト順で以降の欄を読みます。C++の`struct`をそのままファイルに重ねると、処理系のパディングやエンディアンに読み方が依存します。保存形式が定めたバイト列から、一つずつ値を組み立てます。[構造体とメモリレイアウト](/runtime/cpp-internals/memory-layout.html) · [MicrosoftのPE仕様にあるヘッダーと索引の検査](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#optional-header-image-only)

## 件数を掛ける前に、入る件数を求める

ファイル全体が64バイトなら、12バイトのヘッダーより後には52バイトあります。24バイトの索引項目は最大で`52 / 24 = 2`件入ります。件数が3なら、この時点で入力を拒否できます。件数が2なら、索引の終端は`12 + 2 * 24 = 60`です。

固定幅の型で先に`count * 24`を求めると、件数が極端に大きい場合に結果が折り返すことがあります。先に`count <= (file_size - header_size) / entry_size`を確認すれば、その後の掛け算と加算はファイルサイズの範囲に収まります。これとは別に、アプリで扱える最大件数や索引サイズを設定します。ファイル上で成立する件数でも、そのまま全件の管理領域を確保できるとは限りません。[C++の整数演算の範囲](https://eel.is/c++draft/basic.fundamental#2)

## データの開始位置と長さを順に調べる

オフセットと長さを`offset`と`length`とすると、対象は`[offset, offset + length)`です。右端の位置は範囲に含めません。次の順番なら、検査中に危険な加算をせず、`file_size - offset`が負になる条件も避けられます。

```cpp
#include <cstdint>

bool fits(std::uint64_t file_size, std::uint64_t offset, std::uint64_t length) {
    return offset <= file_size && length <= file_size - offset;
}
```

`&&`は左側が成立したときだけ右側を評価します。実践の壊れた索引と同じく、開始位置を`0xfffffffe`、長さを`4`として32ビットの符号なし型で足すと、値は`2`へ折り返します。この和だけをファイルサイズと比べると、範囲外の開始位置を見落とします。検査を通した後に配列添字やAPIの引数へ変換する場合も、その型が値を表せることを確かめます。[C++の論理積の評価順序](https://eel.is/c++draft/expr.log.and) · [C++の符号なし整数演算](https://eel.is/c++draft/basic.fundamental#2)

ファイルに収まると分かっても、形式が指定した領域かを確認します。図の`[59, 60)`はファイル内の索引を指します。データを読むなら、`offset >= 60`も必要です。長さ0を許すか、データ範囲の共有を許すか、同じ名前が現れた場合をどう扱うかも形式で決めます。実践では索引がデータの開始位置順に並ぶと定め、直前の終端が次の開始位置を越えたら拒否します。名前は小文字の英字・数字・`_`・`-`からなる1～15文字で、残りのバイトをNULで埋め、重複を拒否します。[アセットパックの索引とデータ](/game/asset-pack-files.html)

## 構造の検査から、内容と資源量の検査へ

索引から切り出した範囲が正しくても、画像ならピクセルの形式、メッシュなら頂点数とインデックスなどを、そのデータ形式の規則で検査します。たとえばメッシュのインデックスが参照する頂点番号は、読み込んだ頂点数より小さい必要があります。ファイルを分割して読む場合は、実際に読めたバイト数も確認します。ファイルのサイズを取得してから読み取るまでに内容が変わり得る構成なら、同じ版のデータを読み続けられるよう、読み取り中の更新を防ぐなどの手当てをします。[ファイル読み取りでの実際の読み取り量](/os/file-read-journey.html) · [アセットを利用可能にする条件](/game/asset-loading.html)

圧縮データには、入力範囲の上限、出力バイト数の上限、展開器の作業メモリの上限を設けます。ヘッダーの展開後サイズを検査してから確保し、展開中も実際の出力量を制限します。Zstandardの仕様でも、フレームが要求する展開用ウィンドウが実装の許容範囲を超えたら拒否できます。[RFC 8878のZstandardフレーム仕様](https://www.rfc-editor.org/rfc/rfc8878.html#name-window_descriptor)

チェックサムは保存や転送で起きた破損を検出する手掛かりです。配布元を確かめるには、信頼済みの公開鍵でデジタル署名を検証する方法があります。秘密鍵を共有する構成では、メッセージ認証コード（MAC）で共有鍵を持つ側が認証したデータかを確かめられます。照合に成功したファイルも、受け入れる版や展開量など、読み手の条件を満たすか検査します。[RFC 1952のCRC32](https://www.rfc-editor.org/rfc/rfc1952.html#section-2.3.1) · [NISTのデジタル署名仕様](https://csrc.nist.gov/pubs/fips/186-5/final) · [RFC 2104のメッセージ認証コード](https://www.rfc-editor.org/rfc/rfc2104.html#section-1)

実践では、パックを生成して名前からアセットを読み、壊れた索引がデータの読み取り前に拒否される様子を確認できます。[C++でアセットパックを観察する](/practice/io/asset-pack-observation.html)
